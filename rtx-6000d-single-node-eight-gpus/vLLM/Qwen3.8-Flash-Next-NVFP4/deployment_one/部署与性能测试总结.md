## 1. 部署

### 1.1 部署形态

| 项目    | 内容                                                                             |
| ----- | ------------------------------------------------------------------------------ |
| 容器镜像  | `vllm/vllm-openai:v0.31.0`（`docker run -it --rm` 前台运行）                         |
| GPU   | `--gpus all` 使用全部 8 张卡，`--shm-size=32g`                                        |
| 网络    | `--network host`，OpenAI 兼容接口 `http://127.0.0.1:8000`                           |
| 模型挂载  | 宿主机 `/data/models/rtx-6kd/nv-community/Qwen3.8-Flash-Next-NVFP4` → 容器 `/model` |
| 对外服务名 | `Qwen3.8-Flash`（`--served-model-name`）                                         |
| 部署状态  | ✅ 启动成功（原文档记录）                                                                  |

### 1.2 启动命令

```bash
docker run -it --rm \
  --gpus all \
  --shm-size=32g \
  --network host \
  -v /data/models/rtx-6kd/nv-community/Qwen3.8-Flash-Next-NVFP4:/model \
  -e VLLM_USE_RUST_FRONTEND=1 \
  vllm/vllm-openai:v0.31.0 /model \
  --served-model-name Qwen3.8-Flash \
  --gpu-memory-utilization 0.8 \
  --quantization modelopt \
  --enable-expert-parallel \
  --tensor-parallel-size 8 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}' \
  --kv-cache-dtype fp8 \
  --attention-config.indexer_kv_dtype fp8 \
  --no-enable-flashinfer-autotune \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --reasoning-parser qwen3 \
  --enable-prefix-caching \
  --enable-prompt-tokens-details
```

### 1.3 关键参数说明

| 参数                                                                   | 说明                                                         |
| -------------------------------------------------------------------- | ---------------------------------------------------------- |
| `--quantization modelopt`                                            | 加载 NVFP4 量化权重（ModelOpt 量化格式）                               |
| `--tensor-parallel-size 8`                                           | 8 卡张量并行（TP=8）                                              |
| `--enable-expert-parallel`                                           | MoE 专家并行（EP）                                               |
| `--speculative-config '{"method":"mtp","num_speculative_tokens":3}'` | **MTP 投机采样解码**：每步投机生成 3 个 token，验证通过则一次输出多个 token，显著提升解码速度 |
| `--kv-cache-dtype fp8`                                               | KV Cache 以 FP8 存储（降低显存占用、提升带宽效率）                           |
| `--attention-config.indexer_kv_dtype fp8`                            | 注意力 indexer（Qwen3-Next 类稀疏注意力索引结构）的 KV 同样使用 FP8            |
| `--gpu-memory-utilization 0.8`                                       | 显存利用率上限 80%                                                |
| `-e VLLM_USE_RUST_FRONTEND=1`                                        | 启用 Rust 前端（Tokenizer / 请求解析加速）                             |
| `--no-enable-flashinfer-autotune`                                    | 关闭 FlashInfer 自动调优                                         |
| `--enable-auto-tool-choice` + `--tool-call-parser qwen3_coder`       | 启用工具调用（Function Calling）解析                                 |
| `--reasoning-parser qwen3`                                           | 思维链（Reasoning）内容解析                                         |
| `--enable-prefix-caching`                                            | 启用前缀缓存                                                     |
| `--enable-prompt-tokens-details`                                     | 返回 `prompt_tokens_details`（含 `cached_tokens`），用于统计缓存命中     |

## 2. 性能测试

> ⚠️ 性能测试脚本文档 `run-perf-test.txt` 为**空文件（0 字节）**。以下测试细节依据结果目录中 AIPerf 日志的 CLI 回显与 `summary.csv` 还原。

### 2.1 测试工具与命令

- **工具**：NVIDIA AIPerf（`aiperf profile`），OpenAI **chat** 端点、**streaming** 流式输出
- **Tokenizer**：`/data/models/rtx-6kd/Qwen3.8-Flash-Next`
- **每场景命令**（从日志回显还原，`{}` 为批量脚本的循环变量）：

```bash
aiperf profile --model 'Qwen3.8-Flash' \
  --tokenizer '/data/models/rtx-6kd/Qwen3.8-Flash-Next' \
  --endpoint-type 'chat' \
  --url 'http://127.0.0.1:8000' \
  --isl {1000|8000|16000|32000|64000|128000} \
  --osl 1000 \
  --streaming \
  --request-count 10 \
  --concurrency {1|4|8}
```

**要点**：

- 命令中**无 `--shared-system-prompt-length`** → 每个请求为独立全量输入，**不共享前缀**（与 deployment_two 的 90% 前缀缓存测试设计不同）；
- 日志提示全程未观察到 `prompt_tokens_details.cached_tokens`（无前缀缓存命中），与独立输入设计一致；
- 数据集采样策略 `sequential`，每场景 10 个对话 = 10 个请求，`concurrency_burst` 并发模式。

### 3.3 结果分析

1. **稳定性**：18/18 场景全部成功（错误率 0），128k 输入 + 8 并发下无失败请求。
2. **单用户解码性能（MTP 投机采样收益明显）**：
   - 并发 1 时 ITL 稳定在 **5.21–5.52 ms**，对应 **182–194 tokens/sec/user**，且几乎不随输入长度变化（≤128k 内 MTP 加速稳定）；
   - 对比同平台无 MTP 配置（deployment_two：ITL 8.5–8.7 ms、115–118 tokens/sec/user），单用户解码速度约 **1.6 倍**（两次测试输入构造不同，倍数仅供参考）。
3. **并发对解码的冲击远大于输入长度**：
   - 并发 1→8、输入 1k→128k 时，avg ITL 从 5.46 ms 恶化到 **52.96 ms**（p99 90.83 ms），单用户解码从 185.09 降至 **34.98 tokens/sec/user**（仅剩 19%）；
   - 高并发 + 长上下文下 MTP 优势基本丧失：投机验证开销随 batch 增大、接受率下降，叠加 prefill/decode 争抢算力。8 并发/128k 的 avg ITL（52.96 ms）甚至显著高于 deployment_two 无 MTP 配置同类场景（16.15 ms），提示该场景下 MTP 可能反噬，建议开关对比验证。
4. **总输出吞吐扩展效率低**：
   - 峰值 **976.64 tokens/sec**（8 并发/1k），仅为并发 1 的 **5.3 倍**（理想线性 8 倍）；
   - 长输入下更差：4 并发/128k 总吞吐 189.12 ≈ 并发 1 的 183.88（**几乎零增益**），8 并发/128k 也仅 279.84（1.5 倍）。
5. **TTFT 严格线性于输入长度（全量 prefill、无缓存命中）**：
   - 并发 1 时 1k→100 ms、128k→10.36 s（约 104 倍），折算 prefill 速率恒定 ~12,300–12,500 tokens/sec/user，说明每个请求都做了完整 prefill；
   - 并发放大排队与尾延迟：8 并发/128k avg TTFT 40.04 s，**p99 达 82.51 s**（avg 的 2.06 倍）；而并发 1 时 p99 ≈ avg（如 106.2 vs 100.0 ms），无排队时延迟极稳定。
6. **Prefill 吞吐饱和于 ~3.5 万 tokens/sec**：并发 ≥ 4 后总 Prefill 吞吐稳定在 31,700–36,130 tokens/sec，峰值 36,130.04（4 并发/64k）；1k 短输入时（22,498–27,918）批次打不满，未达饱和。
7. **与 deployment_two（90% 前缀缓存测试）不可直接对比**：两者部署配置（本组 MTP + FP8 KV，另一组无）与测试设计（本组全量 prefill 独立输入，另一组 90% 共享前缀）均不同。最直观的差异是 128k 并发 1 的 avg TTFT：本组 10.36 s vs 另一组 2.97 s，主要由前缀缓存命中贡献。

### 3.4 结论与建议

**结论**

- MTP（3 tokens 投机）+ FP8 KV Cache 配置下，**低负载解码性能优秀**：单用户 182–194 tokens/sec、ITL ~5.5 ms，且在 128k 以内不随上下文长度衰减；
- **Prefill 能力有上限**：单用户 ~12.4k tokens/sec，多并发总吞吐饱和于 ~3.5 万 tokens/sec；无缓存命中时 128k 输入首响需 10.4 s（并发 1）；
- **并发扩展性是短板**：解码总吞吐峰值 976.64 tokens/sec（8 并发/1k，5.3×）；长输入下 4 并发解码几乎零增益、8 并发仅 1.5 倍，且 8 并发/128k 出现 TTFT p99 82.5 s、ITL p99 90.8 ms 的严重尾延迟；
- 18 个场景全部 100% 成功，服务稳定性良好。

**建议**

1. **补全 `run-perf-test.txt`**（当前为空文件），记录批量脚本与参数，便于复现；
2. 查明 **conc=2 数据未纳入汇总** 的原因（日志有效），补入 summary 或说明剔除依据；
3. 针对高并发长输入场景做 **MTP 开/关对照测试**，量化投机采样在重负载下的收益/开销，必要时按负载动态开关；
