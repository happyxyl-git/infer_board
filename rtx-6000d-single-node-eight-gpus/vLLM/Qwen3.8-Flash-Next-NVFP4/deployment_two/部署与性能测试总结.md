## 1. 部署

### 1.1 部署形态

| 项目    | 内容                                                                             |
| ----- | ------------------------------------------------------------------------------ |
| 容器镜像  | `vllm/vllm-openai:v0.31.0`（`docker run -it --rm` 前台运行）                         |
| GPU   | `--gpus all` 使用全部 8 张卡，`--shm-size=32g`                                        |
| 网络    | `--network host`，OpenAI 兼容接口 `http://127.0.0.1:8000`                           |
| 模型挂载  | 宿主机 `/data/models/rtx-6kd/nv-community/Qwen3.8-Flash-Next-NVFP4` → 容器 `/model` |
| 对外服务名 | `Qwen3.8-Flash`（`--served-model-name`）                                         |
| 部署状态  | ✅ 启动成功，前缀缓存命中率生效（原文档记录）                                                        |

### 1.2 启动命令

```bash
docker run -it --rm \
  --gpus all \
  --shm-size=32g \
  --network host \
  -v /data/models/rtx-6kd/nv-community/Qwen3.8-Flash-Next-NVFP4:/model \
  -e VLLM_USE_RUST_FRONTEND=1 \
  vllm/vllm-openai:v0.31.0 /model \
  --served-model-name Qwen3.8-Flash \
  --gpu-memory-utilization 0.8 \
  --quantization modelopt \
  --enable-expert-parallel \
  --tensor-parallel-size 8 \
  --no-enable-flashinfer-autotune \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --reasoning-parser qwen3 \
  --enable-prefix-caching \
  --enable-prompt-tokens-details
```

### 1.3 关键参数说明

| 参数                                                             | 说明                                                        |
| -------------------------------------------------------------- | --------------------------------------------------------- |
| `--quantization modelopt`                                      | 加载 NVFP4 量化权重（ModelOpt 量化格式）                              |
| `--tensor-parallel-size 8`                                     | 8 卡张量并行（TP=8）                                             |
| `--enable-expert-parallel`                                     | MoE 专家并行（EP）                                              |
| `--gpu-memory-utilization 0.8`                                 | KV Cache 等可占用显存上限 80%                                     |
| `-e VLLM_USE_RUST_FRONTEND=1`                                  | 启用 Rust 前端（Tokenizer / 请求解析加速）                            |
| `--no-enable-flashinfer-autotune`                              | 关闭 FlashInfer 自动调优                                        |
| `--enable-auto-tool-choice` + `--tool-call-parser qwen3_coder` | 启用工具调用（Function Calling）解析                                |
| `--reasoning-parser qwen3`                                     | 思维链（Reasoning）内容解析                                        |
| `--enable-prefix-caching`                                      | 启用前缀缓存（本次性能测试 90% 命中率设计的基础）                               |
| `--enable-prompt-tokens-details`                               | 返回 `prompt_tokens_details`（含 `cached_tokens`），用于验证/统计缓存命中 |

### 1.4 前缀缓存（Prefix Caching）验证

部署成功后，通过**两次完全相同**的请求（携带同一段长共享系统提示词）验证缓存是否生效：

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen3.8-Flash",
    "messages": [
      {"role": "system", "content": "<很长的共享系统提示词（约 100 句重复文本）>"},
      {"role": "user", "content": "测试"}
    ]
  }'
```

- **第 1 次（冷缓存）**：`usage.prompt_tokens_details.cached_tokens` 为 0 或字段缺失；
- **第 2 次（相同前缀）**：`cached_tokens > 0`，证明共享前缀的 KV 缓存被复用，前缀缓存生效。

## 2. 性能测试

### 2.1 测试方法

- **工具**：NVIDIA AIPerf（`aiperf profile`），OpenAI **chat** 端点、**streaming** 流式输出
- **Tokenizer**：`/data/models/rtx-6kd/Qwen3.8-Flash-Next`
- **服务地址**：`http://127.0.0.1:8000`
- **批量脚本**：`run-prefix-cache.sh` —— 双层循环（并发 × 输入长度），逐场景执行并保存日志，最后写入 `summary.csv` 汇总
- **固定参数**：每场景 `--request-count 10`，`--osl 1000`（输出 1000 tokens）
  - 注：脚本未加 `--extra-inputs ignore_eos:true / min_tokens:<N>`，OSL 由服务端尽力保证，个别请求可能因提前命中 EOS 而略短

共 **4 × 6 = 24 个场景**。

### 2.3 前缀缓存命中率设计（目标 ≥ 90%）

脚本将每个输入长度按 90 : 10 拆分为**共享系统提示词**（shared）与**独立输入**（isl）：

```
shared = ceil(L × 0.9)    # 向上取整
isl    = floor(L × 0.1)   # 向下取整，至少为 1
保证 shared / (shared + isl) ≥ 0.90
```

| 目标输入长度 (tokens) | shared-prompt | isl    | 实际命中率  |
| ---------------:| -------------:| ------:| ------:|
| 1,000           | 900           | 99     | 0.9009 |
| 8,000           | 7,200         | 799    | 0.9001 |
| 16,000          | 14,400        | 1,599  | 0.9001 |
| 32,000          | 28,800        | 3,199  | 0.9000 |
| 64,000          | 57,600        | 6,399  | 0.9000 |
| 128,000         | 115,200       | 12,799 | 0.9000 |

> 含义：同场景内 10 个请求共享同一段系统提示词（占输入的 90%），后续请求可复用该前缀的 KV 缓存，仅独立部分（10%）需要重新 prefill。这模拟了多轮对话 / 多租户共享长 System Prompt 的真实业务形态。

### 3.3 结果分析

1. **稳定性**：24/24 场景全部成功（Request Error Rate = 0，Success Rate = 100%），128k 长输入 + 并发 8 下服务无失败、无超时。
2. **TTFT（首 token 延迟）**：
   - 随输入长度近似线性增长：并发 1 时 1k→72ms、128k→2,973ms（约 41 倍），与 prefill 计算量随长度增长的规律一致；即使有 90% 前缀缓存，首次请求仍需完整 prefill，后续请求也仍需处理 10% 独立部分及全长度 attention；
   - 并发放大排队效应：128k 输入下并发 1→8，avg TTFT 2.97s→18.64s（6.3 倍），p99 最高达 27.15s；
   - 个别反常点（并发 4/1k 的 111ms 低于并发 2/1k 的 159ms）与批调度节奏、前缀缓存命中时机有关，且每场景仅 10 个请求，存在统计波动。
3. **ITL（token 间延迟）与解码性能**：
   - 并发 1 时 ITL 稳定在 8.5–8.7ms（≈115–118 tokens/sec/user），几乎不随输入长度变化；
   - 并发升高后 ITL 抬升：并发 8 时 11.13ms（1k）→ 16.15ms（128k），p99 最高 27.09ms（8/128k）；
   - 总解码吞吐在并发 8/1k 达峰值 **722.96 tokens/sec**，仅为并发 1 的约 6.2 倍（理想线性应为 8 倍），且输入越长差距越大（8/128k 仅 533 tokens/sec）——解码阶段受显存带宽与 TP 通信限制，并发扩展效率有限。
4. **Prefill 吞吐**：
   - 单用户 Active Prefill 吞吐随输入长度上升（并发 1：13.8k @1k → 43.6k @64k tokens/sec/user），长序列摊薄了调度与 kernel 启动开销；
   - 总 Prefill 吞吐随并发、长度双增长，在并发 ≥ 4~8 且输入 ≥ 32k 时趋于饱和，峰值约 **111.2k tokens/sec**（8/64k）；
   - 短输入（1k）场景下 Prefill 总吞吐明显偏低（并发 1 仅 13.8k、并发 2 反而降至 9.9k），原因是可并行 prefill 的 token 总量少、批次不易打满，该口径此时参考意义有限。
5. **压力最大组合**：并发 8 + 输入 128k —— avg TTFT 18.64s（p99 27.15s）、ITL 16.15ms（p99 27.09ms）、单用户解码降至 66.63 tokens/sec/user，为全部场景中的延迟与单用户体验下限。

### 3.4 结论与建议

**结论**

- RTX 6000D 单机八卡 + vLLM v0.31.0（TP=8 + EP + NVFP4）可稳定服务最长 128k tokens 输入，24 个场景零失败；
- Prefill 能力充裕：长输入下总吞吐稳定在 9–11 万 tokens/sec；
- 解码吞吐是瓶颈：总输出吞吐峰值约 723 tokens/sec（8 并发短输入），高并发长输入时降至约 533 tokens/sec，单用户速度随并发明显衰减（116 → 67 tokens/sec/user）；
- 90% 前缀缓存设计下，TTFT 仍主要受总输入长度与并发排队影响。

**建议**

1. 增大每场景请求数（当前仅 10），降低统计波动，尤其用于对比相近并发档位；
2. 性能测试脚本补充 `--extra-inputs ignore_eos:true` 或 `min_tokens:<N>`，严格保证 OSL=1000，避免个别请求提前 EOS 影响吞吐/延迟统计；
3. 补充更高并发档（如 16、32）定位总输出吞吐的拐点；
4. 增加一组关闭 `--enable-prefix-caching` 的对照测试，量化 90% 共享前缀带来的实际收益；
5. 长输入高并发（8/128k）场景 TTFT p99 达 27s，如业务对首响敏感，可考虑限制并发或优先保障短输入请求的调度隔离。
